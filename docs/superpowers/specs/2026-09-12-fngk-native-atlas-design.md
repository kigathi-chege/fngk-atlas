# FNGK-Native Atlas Design

## Product intent

FNGK Atlas is a standalone power tool that maps, explains, edits, and operates everything reachable through the effective context of the installed FNGK process. An explicit Files binding is one high-fidelity access route, not Atlas's authorization ceiling. When the current FNGK identity can open a terminal on a Device, Atlas may use that terminal to discover and operate the host to the same extent as that shell user, including a root shell.

Atlas must remain an atlas: files and editing are connected to Devices, repositories, packages, modules, functions, dependencies, processes, containers, ports, tests, coverage, cyclomatic complexity, CRAP, and runtime evidence. It is not a generic editor with a graph attached.

## Trust and integration boundary

Atlas is its own repository and application. It discovers and invokes the installed `fngk` executable; FNGK retains its paired Device and operator credentials. Atlas must not ask for a Signal cookie, team ID, base URL, or duplicate root grant, and must not read FNGK credentials directly.

Signal may be enhanced only with reusable native FNGK primitives, never an Atlas-specific bridge:

- `fngk status --json` emits a versioned, secret-free snapshot of the current profile's authorized namespace.
- `fngk <target> --new --stdio-json` exposes the existing terminal WebSocket as newline-delimited JSON over stdin/stdout. It supports ready/replay/output/input/resize, command queue/completion, Ctrl+C, collaboration controls, nested approvals, errors, detach, and exit.
- Existing interactive commands and output remain compatible.

Atlas declares the minimum FNGK protocol versions. If the installed CLI is too old, Atlas offers a confirmed, streamed `fngk update`, then rechecks the binary, daemon, and namespace. Exact-head development artifacts use the existing FNGK release/install/converge mechanics so the host process can be upgraded before a public release.

## Effective access model

Atlas normalizes evidence from:

1. direct local OS access available to the Atlas process;
2. FNGK namespace and installed adapter evidence;
3. FNGK terminal sessions and ordinary shell commands on authorized Devices.

An operation resolver chooses a route per operation, preferring direct or structured adapter access for fidelity and cost and falling back to terminal access whenever it preserves semantics. Every fact records Device, transport, effective identity/privilege, timestamp, freshness, and failure state. A resource may combine evidence from multiple routes.

Automatic discovery is read-only. Atlas does not install helpers or leave discovery files on explored hosts. Shell probes are generated by OS/shell-specific adapters and use framed in-memory output. Explicit file saves may use a same-directory temporary file for atomic replacement and must remove it on success or failure.

Atlas maps all visible paths, processes, services, code, and runtime relationships, but redacts secret-bearing values in derived and persisted records. Authorized users may open original content on demand. Active file buffers are not persisted as an unencrypted host mirror.

## Discovery and analysis

Startup performs a bounded, cancellable, rate-limited census for every authorized Device: identity and privilege, mounts/filesystems, top-level paths, repositories/worktrees, package manifests, services, processes, containers, listening ports, adapters/resources, and coverage artifacts. Virtual and pathological trees are modeled without recursive copying. Partial results appear while deeper work continues.

Repository analysis is context-first and lazy. It identifies repositories, packages/workspaces, modules, symbols/functions, parameters, imports, calls, tests, generated/vendor code, Git revision, complexity, and runtime links. Existing LCOV, Cobertura, coverage.py, and Go coverage are normalized to source spans. CRAP uses `complexity^2 * (1 - coverage)^3 + complexity`, with coverage expressed from 0 to 1. The UI shows formula version, evidence artifact, revision, and freshness; CRAP is unavailable rather than invented when coverage cannot be matched. Coverage refresh is an explicit terminal-backed test command.

SQLite persists derived facts, hashes, spans, metrics, redacted metadata, evidence provenance, layouts, and run summaries. File/process/repository changes invalidate only affected facts. Offline Devices preserve last-observed facts as stale.

## Workbench and interaction

The browser UI uses Svelte 5, TypeScript, Vite, Dockview, CodeMirror 6, Cytoscape, and a themed PTY emulator. The default desktop layout is a left Atlas navigator, central Dockview workspace, right filesystem explorer, and bottom activity/status strip. Dock panels include semantic graphs, files, terminals, process logs/details, function metrics, coverage, diffs, and run output.

The right explorer browses the effective filesystem, including terminal-only paths. Opening a file creates a CodeMirror panel with language support, source-span navigation, search/replace, dirty state, explicit save, reload, and ETag/fingerprint conflict resolution. Saves are atomic and never silently overwrite a changed file.

The terminal is a native Atlas panel, not a foreign embedded page. It shares Atlas typography, colors, tabs, status language, context menus, and selection state while preserving full PTY behavior: ANSI rendering, resizing, stdin, Ctrl+C, prompts, full-screen programs, replay, attach/detach, stop/restart, collaboration, and nested approvals. Atlas adds Device, session, cwd, command, process, repository/function, recording, and lifecycle context around it.

The graph is a linked set of bounded lenses:

- World: profiles/teams to Devices, Connections, contexts, and resource families.
- Machine: filesystems, repositories, services, processes, containers, and ports.
- Code: repository to package/workspace to module, aggregating folders unless useful.
- Function: a symbol's callers, callees, tests, runtime evidence, complexity, coverage, and CRAP.
- Execution: commands/functions/tests to terminal sessions, processes, output, coverage, and changed artifacts.

Each lens enforces a visible-node budget, aggregates hidden descendants, groups strongly connected modules, and uses explicit expansion nodes. Containment, imports, calls, runtime, coverage/test, and deployment edges are switchable. Deterministic layered layout, minimap, breadcrumbs, navigation history, saved positions, search, focus-neighborhood, and source-span opening preserve readability. Selection is shared across graphs, editors, files, processes, and terminals.

## Operations and safety

All actions use one operation lifecycle: resolve target, enumerate routes, select the best route, disclose effective Device/user/cwd/command and risk when needed, stream progress, record provenance/summary, and invalidate affected facts.

Read-only census probes run automatically. File saves, test/coverage runs, arbitrary function or project commands, process controls, and privilege escalation are explicit actions. Destructive actions, stale overwrites, elevation, and production-targeted commands add typed confirmation. Atlas does not add blanket confirmation to every FNGK operation.

Function execution is language-aware and honest. Atlas generates a harness only for symbols that can be invoked with serializable inputs in their real repository context. Otherwise it offers the containing test, a detected project command, or an editable terminal launch configuration. Output, exit status, duration, revision, non-secret environment keys, and resulting coverage remain linked evidence.

Distinct failure states include missing/outdated FNGK, unpaired profile, operator login required, offline Device, denied capability/elevation, stale file, partial scan, parser failure, unsupported runtime, stale coverage, and timeout. Route fallback is allowed only when semantics are preserved. Last observed never means currently accessible.

## Acceptance

The implementation is accepted only after a disposable live integration starts Signal's PostgreSQL/Redis stack with terminals enabled, builds an exact-head FNGK CLI, pairs and logs in a disposable Device, runs its daemon/adapters, and proves Atlas can:

- load the authorized namespace without receiving credentials;
- discover root-visible host facts beyond a Files binding without helper artifacts;
- browse, edit, conflict-check, and save a file;
- map a process to its repository/module/function evidence;
- run and interrupt a terminal command;
- ingest or refresh coverage and calculate CRAP;
- handle disconnect/reconnect and stale evidence;
- render the Dockview workbench and bounded graph lenses without browser console errors.

The handoff documents exact-head host installation, daemon convergence, launch, verification, and rollback. Development never mutates the real host installation or production deployment automatically.
